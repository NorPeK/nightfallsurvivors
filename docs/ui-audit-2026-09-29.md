# UI, input and contrast audit — 2026-09-29

This is a source audit with numeric CSS contrast calculations and focused automated regressions. It is not a claim of screen-reader certification, physical mobile testing, or release-build frame-rate performance. Browser observations are recorded separately by the parent audit.

## Numeric CSS text contrast

The threshold is 4.5:1 for normal text and 3:1 for qualifying large text, following [W3C's contrast-minimum explanation](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html). Disabled controls and decorative sigils are outside these text checks. The report does not treat text shadow as a dependable background.

Method: composite each translucent surface over white as a conservative bound for bright canvas pixels; composite nested panel surfaces over the resulting overlay. Choose the lightest applicable gradient/hover surface for light text. Convert each resulting sRGB channel to linear light (`c/12.92` for `c <= .04045`, otherwise `((c+.055)/1.055)^2.4`), then compute luminance using `.2126 R + .7152 G + .0722 B`. Contrast is `(lighter+.05)/(darker+.05)`. Displayed ratios are rounded only for reporting; comparisons use full precision. The `.77` ordinary overlay was conservatively rounded down to `196/255` for the table, giving a slightly brighter background than the actual CSS.

The old hero surface could fall to 1.78:1 for copy and 1.59:1 for its eyebrow against a white canvas bound; bright moon pixels also reduced contrast. The old boss announcement was 3.25:1 under the same bound, below normal-text requirements. The old save status was only 4.52:1 over the ordinary `.77` overlay and had no independent backing on the weaker hero overlay. The timer and boss name had no bounded contrast over arbitrary combat effects.

## Local QA diagnostics and capture

`GameRoot` gates the QA lab and diagnostics behind a non-production build and `?debug=1`. That mode loads an isolated temporary profile and bypasses load/save. Production users cannot activate it with the query string.

The existing QA lab now exposes a DOM-readable diagnostics section:

- At most 600 rolling intervals between canvas RAF callbacks, average FPS (`1000 / mean interval`), and nearest-rank p50/p95/p99 in milliseconds.
- Sample count, interval/frame count since reset, CSS viewport size, raster DPR, and current active enemies/projectiles/pickups/particles/effects.
- Values refresh at most once per second during play. Frozen scenes can publish their final values when invalidated. No extra timer or measurement RAF is created; platform/manual pause gaps are excluded by clearing the previous frame timestamp.
- Reset clears the buffer. Launching a fresh QA hunt also resets it. Data stays in component memory and is neither saved nor sent anywhere.
- “Capture battlefield PNG” downloads the actual current canvas pixels through `toBlob`. It excludes DOM HUD/menus, reports unavailable/null captures, and revokes its temporary object URL. It creates no synthetic marketing artwork.

These are development-build frame intervals with QA observer overhead, not engine CPU measurements, GPU timings, or proof of mobile/release performance. Opening the QA controls changes the visible DOM and may itself affect timings; report that condition with captured results.
